## 答え合わせの結果

**再発見 0 / 部分的 1 / 再発見されず 11(全12箇所)**

- 部分的1件は「要承認と例外承認の定義循環」(AMB-01)。事後承認だけで完了まで到達した
  経路と、例外承認の可否を確認している最中に案件が完了まで進んだ経路(場面/世界の
  識別名と引用つき)が、この欠陥が増幅するリスクの顕在化として資料から特定された。
  ただし素通りの理由をこの欠陥**だけ**で説明する記述は資料に無い、という判定
- 前回の暫定照合(要約文書ベース)では「統制ポイントの粒度不足」が部分的だったが、
  今回(実データベース)は「承認の定義循環」が部分的になった。**両者は資料が異なる
  ので同じ測定の再試行ではない**が、資料が変われば「部分的」の対象も変わるという
  事実はここに記録する(判定のばらつきを測らない方針は維持)

## この試運転から言えること

1. **「素通りの経路そのもの」は実データから明確に特定・引用・再現できる。** この装置の
   主たる出力(個別の事実としての素通り経路)は、実データで機能した
2. **「その素通りが、どの規程の欠陥を通り道にしたか」は今の資料からは特定できない。**
   理由は2つ:
   - 今回の20場面は全て同じ案件類型(承認必須の急ぎ・高齢でないお客様)×同じ分岐位置
     (顧客対応の直後)であり、多くの欠陥(高齢の定義不在など)はこの範囲では
     **原理的に発火しない** → 検査範囲の拡大(実装済み)を実データに適用する本実行が必要
   - 確認役の判定理由は「何が起きたか」を述べるが「なぜ規程上それが通ったか」までは
     踏み込まない。機序の特定には、確認役が判定時に規程・世界一式の記録まで遡って
     照合できる形が要る(将来課題として記録。生成側に規程を見せない方針は変えない)

## 費用のかかる試運転について(未実施の理由と、実施できる最小案)

- **この実行環境には接続先の鍵(`OPENROUTER_API_KEY`)が設定されておらず、
  `.env.local` も無い。** 分岐実行(社員・お客様が動く継続)はこの環境では実行できない
- 鍵があれば実行できる**最小の試運転案(推奨)**: 決着しなかった17世界のうち2〜3世界を
  深さ1で再分岐する(木の自動展開の実運転)。今回の生データに含まれる分岐後の世界
  一式からそのまま分岐でき、**元の20本の世界は不要**。規模: 2〜3場面×2〜3分岐=
  6〜9世界、概算 **0.5〜0.9クレジット**(1世界0.07〜0.1として。残高約8.5の1割程度)
- 一方、**場面の全列挙(検査範囲の拡大)の確定値**には元の20本の世界
  (`runs/phase3_m3_confirmatory_v4_20260724` など)が必要で、今回の生データには
  含まれていない。全列挙を回す場合は元の世界一式が置いてある環境で
  `scripts/enumerate_decision_points.py` を実行する(費用ゼロ)
- 実施方法はどちらか: ①この環境(Claude Code on the web)の環境設定に
  `OPENROUTER_API_KEY` を追加して再指示 ②お手元の環境で実行
